# blog-watcher MVP 要件・設計

## 1. 目的

blog-watcherは、設定した情報源を定期的に確認し、キーワードに一致する新着記事をメールで通知するバッチアプリケーションである。

MVPではRSSを取得方式として実装する。ただし、RSSは記事を発見する入力方式の一つとして扱い、既読判定や通知処理をRSS固有のデータ構造へ依存させない。

また、C#と.NETの学習・アウトプットを目的とし、DI、設定、ログ、テストなど、実務で利用しやすい構成を採用する。

## 2. スコープ

### 2.1 MVPに含めるもの

- RSSからの記事取得
- キーワードによる記事の抽出
- URLを使った既読判定
- Cloudflare Workers KVへの状態保存
- Gmail SMTPによるプレーンテキストメール送信
- GitHub Actionsによる定期実行と手動実行
- 副作用を発生させないドライラン
- 単体テストと、偽の外部サービスを使った統合テスト
- Nix Flakeとdirenvによるローカル開発環境

### 2.2 MVPに含めないもの

- LLMによる記事要約
- LLMのフォールバック
- OSSリリース監視
- RSS以外の取得実装
- 記事の更新検知と再通知
- 複数宛先へのメール送信
- テストカバレッジの計測、レポート、閾値

将来機能の空実装や未使用の設定は作らない。一方、記事取得、フィルタリング、通知モデル作成、メール送信、状態保存を分離し、後から要約などの処理ステップを追加できるようにする。

## 3. 監視設定

監視対象はリポジトリ内のJSON設定で管理する。認証情報は含めない。

各監視元は少なくとも次の値を持つ。

| 項目 | 説明 |
| --- | --- |
| `Id` | 初期化状態の管理に使う、変更しない識別子 |
| `Name` | メールやログに表示する名前 |
| `Type` | 記事の取得方式。MVPでは`rss`のみ |
| `Url` | RSSフィードなど、取得方式に対応するURL |
| `Keywords` | OR条件で照合する1件以上のキーワード |

初期設定は次のとおりとする。

| Id | Name | Type | Url | Keywords |
| --- | --- | --- | --- | --- |
| `mercari-engineering` | Mercari Engineering Blog | `rss` | `https://engineering.mercari.com/blog/feed.xml` | `TiDB` |
| `read-uncommitted` | READ UNCOMMITTED | `rss` | `https://read-uncommitted.com/rss.xml` | `TiDB WEEKLY` |

未知の`Type`、重複する`Id`、空のキーワード、不正なURLなどは起動時の設定エラーとし、外部通信を始める前にジョブを失敗させる。

## 4. 共通記事モデル

取得したデータは、取得方式に依存しない共通モデルへ変換する。

| 項目 | 必須 | 用途 |
| --- | --- | --- |
| `SourceId` | はい | 取得元の識別 |
| `SourceName` | はい | メールとログへの表示 |
| `Title` | はい | 通知内容 |
| `Url` | はい | 記事の同一性と通知内容 |
| `PublishedAt` | いいえ | 通知への表示。新着判定には使わない |
| `SearchableText` | はい | キーワード判定 |

RSSの場合、`SearchableText`は取得できたタイトル、概要、本文を連結して作る。記事ページのHTMLは取得しない。

## 5. キーワード判定

- タイトル、概要、本文のうちRSSから取得できた項目を対象にする
- 大文字小文字を区別しない部分一致とする
- 1つの監視元に複数キーワードがある場合はOR条件とする
- キーワードに一致しない記事は既読状態へ保存しない

最後のルールにより、既存記事が後から編集されてキーワードに一致し、RSS上で再取得できた場合は、その時点で通知候補になり得る。

## 6. 記事の同一性とURL正規化

RSSのGUIDには依存せず、正規化した記事URLを記事の識別に使う。既読用のKVキーは、正規化URLからSHA-256ハッシュを生成して作る。

URL正規化は誤った同一視を避けるため、次の安全な範囲に限定する。

- スキームとホスト名の大文字小文字を正規化する
- 既定ポートを正規化する
- フラグメント（`#...`）を除去する
- クエリ文字列は保持する
- 末尾スラッシュは保持する

同じ正規化URLの記事は、タイトルや本文が後日変わっても再通知しない。1回の取得結果内に同じ正規化URLが複数回現れた場合は1件へまとめる。監視元横断の高度な重複統合や優先順位付けは行わない。

URLがない、またはURLが不正な記事は、警告ログを残して記事単位で除外する。フィード全体を解析できない場合、または取得した全記事が不正な場合はジョブを失敗させる。

## 7. 初回実行

監視元ごとに初期化済みかをCloudflare Workers KVで管理する。

初回の実行モードでは、キーワードに一致する既存記事を既読として保存するが、新着としては通知しない。その日のメールは通常と同じ「新着記事はありません」とし、初回専用の文言は加えない。

初期化途中で失敗した場合に次回の既存記事が新着扱いされないよう、記事の既読状態を保存した後で、その監視元を初期化済みにする。監視元が初期化済みになるまでは、その監視元の一致記事を通知しない。

ドライランでは初期化状態を含めて読み取るが、既読記事と初期化状態は保存しない。

## 8. 通常実行フロー

処理は概念的に次の順序で行う。

1. 設定と必要な環境変数を検証する
2. 全監視元から記事を取得する
3. 共通記事モデルへ変換する
4. キーワードで抽出する
5. URLを正規化し、処理内の重複を除く
6. Cloudflare Workers KVで既読状態を確認する
7. 将来の要約などを追加できる処理境界を通す
8. 1通分の通知モデルを作る
9. Gmailへメールを送信する
10. メール送信に成功した新着記事を既読として保存する

通知漏れを避けるため、メール送信後に既読状態を保存する。この間に障害が発生した場合、翌回に同じ記事が再送される可能性は許容する。配送保証は厳密なexactly-onceではなく、at-least-onceとする。

複数記事のKV保存中に一部だけ失敗した場合もジョブを失敗させる。メールはすでに送信済みのため、次回は未保存の記事だけが重複して通知される可能性がある。

## 9. メール通知

Gmail SMTPを使用し、Googleアカウントの2段階認証とアプリパスワードで認証する。送信元と送信先は同じ個人Gmailアドレス1件とする。

メールはプレーンテキストで、1回の実行につき1通送信する。

新着がある場合、少なくとも次の内容を含める。

- JST基準の日付
- 新着件数
- 監視元名
- 記事タイトル
- 記事URL
- 公開日時（取得できる場合）

件名の例は`[blog-watcher] 新着2件 - 2026-08-22`とする。

新着がない場合もメールを送信し、本文に「新着記事はありません」と記載する。これは正常終了であり、ジョブを失敗させない。

## 10. 障害時の振る舞い

### 10.1 リトライとタイムアウト

RSS取得、Cloudflare KV操作、SMTP送信には、最大3回の試行とjitter付きexponential backoffを適用する。基本待機時間は1秒、2秒、4秒とする。

- 各通信処理のタイムアウト: 30秒
- GitHub Actionsジョブ全体のタイムアウト: 10分

SMTPの応答が失われた場合、送信済みかを完全には判定できないため、リトライによるまれな重複メールは許容する。

### 10.2 監視元の取得失敗

1つでも監視元の取得が最終的に失敗した場合、不完全な日次結果を送らない。

- メールを送信しない
- 既読状態を更新しない
- ジョブを失敗させる

GitHub Actionsの手動実行でジョブ全体を再実行できるようにする。

### 10.3 状態保存またはメール送信の失敗

- メール送信に失敗した場合は既読状態を保存せず、ジョブを失敗させる
- KV保存に失敗した場合はジョブを失敗させる
- 新着0件は障害ではなく正常終了とする

## 11. Cloudflare Workers KV

GitHub ActionsとローカルアプリケーションからCloudflare APIを直接利用し、専用Workerは作らない。

APIトークンは対象Namespaceへの必要最小限の読み書き権限に限定する。次の値を秘密情報として環境変数またはGitHub Actions Secretsから渡す。

- Cloudflare Account ID
- Workers KV Namespace ID
- Cloudflare API Token

既読記事の値には、少なくとも初回検出日時、監視元名、記事URLをJSONで保存する。有効期限は設定しない。初期化状態は監視元の`Id`を使った別キーで保存する。

ドライランではKVの読み取りだけを許可し、書き込みAPIを呼ばない。

## 12. 実行方式

### 12.1 定期実行

GitHub Actionsのcronを使用し、毎日8:00 JSTに相当する23:00 UTCに実行する。GitHub Actionsの混雑などによる開始時刻の遅延は許容する。

定期実行は常に実行モードであり、メール送信とKV更新を行う。

### 12.2 手動実行

`workflow_dispatch`を用意し、`dry_run`入力を持たせる。デフォルトは`true`とする。

ドライランでは次の処理を行う。

- 実際のRSSを取得する
- 実際のKVから状態を読み取る
- キーワード判定と既読照合を行う
- 判定結果をGitHub Actionsログへ出す

次の副作用は発生させない。

- メール送信
- KVへの記事または初期化状態の書き込み

### 12.3 ローカル実行

ローカル実行もデフォルトをドライランとする。明示的に`--execute`を指定した場合だけメール送信とKV更新を許可する。

## 13. 開発環境と秘密情報

- .NETは実装時点のLTS版を使用する
- SDKバージョンを固定する
- Nix Flakeで.NET SDKと必要な開発ツールを提供する
- ローカル開発ではdirenvを前提とし、`.envrc`で`use flake`する
- 初回セットアップでは`direnv allow`を実行する
- ローカルの秘密情報はGit管理外の`.env.local`へ保存する
- `.env.example`には値を含めず、必要な環境変数名だけを記載する
- GitHub Actionsでは同じ環境変数をSecretsから渡す
- `.envrc`、Nix設定、JSON監視設定へ秘密情報を埋め込まない

CIはdirenvに依存せず、Nix Flakeで定義した環境を直接利用する。

## 14. アプリケーション構成

.NET Generic Hostを使う、1回実行型のコンソールアプリケーションとする。Webサーバーや常駐サービスは起動しない。

Generic Hostの次の機能を利用する。

- DI
- JSONと環境変数による設定
- `ILogger`によるログ
- 起動と正常終了の管理
- `CancellationToken`によるキャンセル伝播

記事取得方式は`Type`に応じてファクトリーが実装を選ぶ。MVPではRSS取得実装だけを登録する。テストではKV、メール、記事取得を偽物へ差し替えられるようにする。

将来の機能追加を想定した責務の境界は設けるが、LLMやOSS監視の未使用インターフェースは作らない。

## 15. ログ

標準の`ILogger`を使い、GitHub Actionsで読みやすいテキスト形式にする。監視元ID、取得件数、抽出件数、既読件数、新着件数、除外件数、リトライ回数を個別フィールドとして記録する。

次の情報はログへ出さない。

- APIトークンやパスワード
- Gmail認証情報
- 記事本文全体
- その他の秘密情報

## 16. テストとCI

### 16.1 単体テスト

xUnitを使用し、少なくとも次を検証する。

- URL正規化
- 大文字小文字を区別しないキーワード部分一致
- 複数キーワードのOR判定
- 同一URLの重複排除
- 通知メールの件名と本文
- 設定値の検証

### 16.2 統合テスト

通常CIでは外部サービスやSecretsを使わず、固定RSSデータ、偽のKV、偽のメール送信先を使用して、少なくとも次を検証する。

- 初回は既存記事を保存するが新着として通知しない
- 初回メールは通常の「新着記事はありません」になる
- 既読記事を通知しない
- 複数の新着記事を1通にまとめる
- 新着0件でもメールを送信し、正常終了する
- 取得失敗時はメール送信と状態更新を行わない
- メール失敗時は状態を更新しない
- メール成功後に状態を更新する
- ドライランでは外部への書き込みを行わない

実RSSと本番KVへの接続は、手動GitHub Actionsのドライランで確認する。

### 16.3 CI

Pull Requestとpush時のCIでは、Nix環境を使って次を検証する。

- 依存関係の復元
- ビルド
- 単体テストと統合テスト
- フォーマット
- リンター

リンターは.NET SDK標準のRoslynアナライザーを中心に使用し、警告をCIエラーとして扱う。カバレッジの計測、レポート、閾値は設けない。

## 17. 受け入れ条件

MVPは、次の条件をすべて満たしたとき完成とする。

1. 指定した2件のRSSを設定から取得できる
2. 各監視元のキーワードをOR条件かつ大文字小文字を区別せず照合できる
3. 初回実行では既存の一致記事が通知されず、KVへ既読登録される
4. 2回目以降は未読の一致記事だけが通知される
5. 複数の新着記事が1通のプレーンテキストメールにまとまる
6. 新着0件でも正常終了し、「新着記事はありません」というメールが送られる
7. メール送信成功後にだけ新着記事が既読登録される
8. 1つでも監視元を取得できなければ、メール送信と状態更新をせずジョブが失敗する
9. 定期実行が毎日8:00 JSTに設定される
10. 手動実行のドライランがデフォルトで有効になり、メール送信とKV書き込みを行わない
11. ローカル実行もデフォルトでドライランになる
12. Nix Flakeとdirenvでローカル開発環境を再現できる
13. CIでビルド、テスト、フォーマット、リンターが成功する
14. Secretsや記事本文全体がログやリポジトリへ記録されない

## 18. 許容する制約とリスク

- GitHub Actionsのcronは8:00 JSTちょうどに始まらない場合がある
- メール送信とKV更新は単一トランザクションではないため、障害時にまれな重複通知が起こり得る
- SMTPの応答喪失とリトライによって重複メールが起こり得る
- URLが変わった同一記事は別記事として扱われる
- クエリ文字列や末尾スラッシュが異なるURLは別記事として扱われる
- RSSに本文がない場合、タイトルと概要だけで判定する
- RSSから消えた記事や、RSSに掲載されない記事は検出できない
